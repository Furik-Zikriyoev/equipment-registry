# Реестр техники

Тестовое задание на позицию Middle Frontend Developer.

SPA для учёта парка строительной техники: список с поиском, фильтрами,
серверной пагинацией и сортировкой, плюс форма создания и редактирования.

**Демо:** https://equipment-registry-two.vercel.app

## Запуск

```bash
npm install
npm run dev
```

Приложение откроется на http://localhost:5173

Бэкенд поднимать не нужно — API эмулируется через MSW прямо в браузере,
второй процесс не требуется.

```bash
npm test          # тесты
npm run lint      # линтер
npm run build     # продакшен-сборка с проверкой типов
```

Разработка и проверка велись в Chrome. В Safari service worker на localhost
ведёт себя нестабильно и может не пропускать запросы через MSW —
это особенность браузера, на продакшен-сборку не влияет.

## Стек и обоснование

| Слой                | Выбор                               | Почему                                                                                                        |
| ------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Сборка              | Vite + React + TypeScript (strict)  | стандарт для SPA, быстрый dev-сервер                                                                          |
| Роутинг             | React Router, `createBrowserRouter` | data router обязателен для `useBlocker` — без него нельзя перехватить уход со страницы с несохранённой формой |
| Серверное состояние | TanStack Query                      | отмена устаревших ответов, кеш, состояния загрузки и ошибки из коробки                                        |
| Форма               | React Hook Form + Zod               | `isValid` / `isDirty` / `isSubmitting` закрывают три требования задания напрямую                              |
| UI                  | Mantine + Tabler Icons              | готовые таблица, селекты, пагинация, модалка — дизайн не оценивается, время ушло в логику                     |
| Мок-API             | MSW                                 | один процесс, запуск одной командой, деплоится на хостинг; полный контроль над логикой поиска                 |
| Тесты               | Vitest                              | нативно работает с Vite, без дополнительной настройки                                                         |

## Как решены гонки запросов

Отдельный раздел, потому что это основная сложность задачи.

Параметры списка (поиск, фильтры, сортировка, страница) входят в `queryKey`.
При изменении любого из них TanStack Query видит новый ключ, отменяет
предыдущий запрос через `AbortSignal` и отправляет новый. Сигнал
пробрасывается в `fetch` в `src/api/units.ts`.

Ответ отменённого запроса отбрасывается и до интерфейса не доходит — при
быстром переключении фильтров устаревшие данные не могут появиться поверх
актуальных.

Асинхронная проверка уникальности гос. номера идёт мимо TanStack Query,
поэтому там гонка решается вручную: `src/features/unit-form/UnitForm.tsx`
хранит номер последнего запроса в `useRef` и игнорирует ответы, пришедшие
не от него.

## Ключевые решения

**Состояние списка живёт в URL.** Фильтры, поиск, сортировка и страница —
единственный источник правды, дублирующего `useState` нет. После перезагрузки
всё сохраняется, ссылкой можно поделиться. Параметры разбираются защитно:
`?page=-5` или `?status=мусор` не ломают приложение, а откатываются
к значениям по умолчанию.

**Смена любого фильтра сбрасывает страницу на первую.** Сброс встроен
в общую функцию обновления параметров, а не расставлен по вызовам —
так его нельзя забыть при добавлении нового фильтра.

**Фильтрация, поиск, сортировка и пагинация — на стороне «сервера».**
В компонентах нет ни одной операции над массивом данных. Вся логика
в `src/mocks/handlers.ts`, и при замене мока на реальный бэкенд клиентский
код не меняется.

**Пробег в форме хранится строкой.** HTML-инпут всегда отдаёт строку;
конвертация в число происходит один раз, при отправке. Это избавляет
от `NaN` в промежуточных состояниях.

**Даты сравниваются как строки формата `YYYY-MM-DD`.** Лексикографический
порядок совпадает с хронологическим, библиотека дат не нужна. Текущая дата
берётся из локального календаря, а не через `toISOString()` — в UTC+5
последний дал бы сдвиг на сутки и пометил бы сегодняшнюю дату как будущую.

**404 и ошибка запроса обрабатываются по-разному.** Для несуществующей
записи кнопка «Повторить» бессмысленна, поэтому там показывается ссылка
на список. Различение возможно благодаря собственному классу `ApiError`
с полем `status`.

**Защита от потери данных различает «трогал поле» и «изменил значение».**
Используется `isDirty` из React Hook Form: если вернуть значение к исходному,
предупреждение не появится.

## Структура

```
src/
  api/        слой запросов — единственное место, знающее про сеть
  app/        провайдеры, роутер, общий каркас страниц
  features/   экраны: units-list, unit-form
  hooks/      переиспользуемая логика
  mocks/      MSW: обработчики и хранилище в памяти
  shared/     общие компоненты, утилиты, константы
  types/      доменные типы
```

## Известные упрощения

- Мок-API не валидирует тело POST и PATCH — предполагается, что это делает
  реальный бэкенд. Клиентская валидация полная.
- Данные хранятся в памяти и сбрасываются при перезагрузке страницы.
- MSW работает и в продакшен-сборке — осознанное решение, чтобы демо
  открывалось по ссылке без поднятия бэкенда.
- Задержка ответов 400 мс задана намеренно: иначе состояния загрузки
  не проявляются и их невозможно оценить.
- Поиск не учитывает раскладку и опечатки — ищет по подстроке в гос. номере
  и модели, без учёта регистра.
- В консоли dev-режима MSW может выводить предупреждение о навигационном
  запросе — известная особенность библиотеки, на работу не влияет.

## Что доработал бы при наличии времени

- Виртуализация таблицы — при росте страницы до сотен строк текущая
  отрисовка начнёт тормозить.
- Оптимистичное обновление при сохранении: сейчас пользователь ждёт ответ
  сервера, хотя результат почти всегда предсказуем.
- Единая типизированная схема query-параметров на Zod, чтобы разбор URL
  описывался декларативно, а не вручную в хуке.
- E2E-тест на сквозной сценарий: отфильтровал → открыл запись →
  отредактировал → сохранил → увидел изменение в списке.
- Массовые операции над выбранными строками и экспорт списка.
